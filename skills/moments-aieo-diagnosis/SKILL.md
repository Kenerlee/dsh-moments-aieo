# AIEO 诊断：bb-browser → 图文诊断报告

诊断 → 定位 → 内容 → 监控。交付可阅读的结论、可复核的指标和可沿用的问题库。

这份报告通常是客户接触我们 GEO 服务的第一站：它既要经得起客户技术负责人逐条核对，也要让老板看完愿意继续合作。两者不冲突——**说服力来自客户能亲眼看到的证据**（AI 原话、截图、逐题矩阵、与官网的逐项对照），而不是夸大的分数。

## 交付约定

沿用客户已有诊断目录；没有约定则使用项目内 `01_diagnosis/`（本套 skill 的定位、监控阶段从这里读取问题库）。不要写入固定用户的绝对路径。

| 交付物 | 文件名 | 用途 |
|---|---|---|
| **最终诊断报告** | `{品牌名}_AIEO诊断报告_{YYYY-MM-DD}.html` | 主交付物（客户版）：只有正文，不含附录；关键截图内嵌 |
| 含证据附录版 | `{品牌名}_AIEO诊断报告_{YYYY-MM-DD}_含证据附录.html` | 同一报告加上背景、官网审计范围、方法与限制、指标口径和全部回答，放进证据压缩包供复核 |
| 证据压缩包 | `{品牌名}_AIEO诊断_完整证据_{YYYY-MM-DD}.zip` | 含证据附录版 HTML、原始快照、全部截图、记录和技术构建文件，随客户版一起发给客户 |
| 问题库初稿 | `{品牌名}_问题库_{YYYY-MM-DD}.md` | 保持定位、内容、监控阶段的输入兼容 |
| 报告数据 | `{品牌名}_AIEO诊断报告_{YYYY-MM-DD}.json` | 题库、样本、人工标注和正文；可重新生成 HTML |
| 指标结果 | `{品牌名}_AIEO诊断报告_{YYYY-MM-DD}.metrics.json` | 构建脚本计算的分子、分母和平台切片 |
| 原始证据 | `evidence/{批次}/{平台}_{问题ID}/` | 原始回答、快照、截图和来源面板，失败同样留档 |

Markdown 可作编辑源，不能替代最终 HTML。HTML 正文、指标和完整回答必须离线可读，外部来源链接只用于进一步核验。客户通常只收到 HTML 一个文件，所以 HTML 里不放指向本地证据文件的相对链接（单独打开会点不开）；需要给客户看的截图放进对应发现的 `screenshots` 内嵌，其余证据进压缩包。

## 1. 确定样本与问题库

读取客户材料及最新 `02_positioning/{品牌名}_问题库_*.md`。确认品牌/产品/品类、官网、地区和语言、受众、目标实体及别名、3–5 个直接竞品、平台、时间范围和测试预算。已有信息直接沿用，关键缺项再询问。

- **先冻结竞争集合与别名字典**：公司、商品名、通用名、品类分别统计。品类识别若包含具体产品实例，区分“品类名称出现”和“实例出现”。正文新增竞品列为发现，不无说明地改变本轮分母。
- **主指标使用不点名任何品牌/竞品的自然发现题**。点名目标、竞品、限定国产等倾向题单独标记，不混入主可见率。每题保存 ID、原文、topic、tags 和 cohort。
- 首次诊断默认拟定 15 道核心题：品类推荐 3、场景选择 3、品牌认知 3、竞品对比 3、产品/购买/售后 3。前 6 道通常属于自然发现，仍须逐题检查。按用户范围调整；扩展与行业题可进入问题库，未测题标记“待测”。
- 平台按市场选择：国内可选豆包、千问、DeepSeek、元宝、Kimi、文心、纳米；国际可选 ChatGPT、Perplexity、Claude、Gemini；行业平台按相关性增加。现场检查可用性，不预设免登录，不固定分母为 9。
- 跨平台原题一致，每题新会话。记录账号记忆/个性化是否未知、模型可见标签、搜索/推理开关、时间及时区；新会话不等于匿名环境。默认每题每平台一条，声明单轮限制；复测另存批次，不覆盖原始记录。

问题库保留品牌信息、Tier 1 核心 / Tier 2 扩展 / Tier 3 行业题、BR/CR/CP/SC/PD 分类及 cohort。列出题目 ID、原题、测试状态、题库版本和下一步定位修订事项。

## 2. 网站技术审计

检查首页、核心产品/服务页、FAQ/知识页。用 curl/WebFetch 检查公开 HTTP 响应、robots.txt、sitemap、canonical、title/description、HTML lang、H1、alt、HTTPS、结构化数据；需要渲染或登录态时用 bb-browser。

检查内容是否直接回答用户问题、事实是否有来源、页面是否可抓取。区分原始 HTML 与渲染结果、当前页面与全站、HTTP 失败与 AI 爬虫封禁，不能从一次 403 推断所有 AI 不可访问。每条问题记录 URL、时间、证据、影响与优先级。

Schema 建议使用与实际内容匹配的 Organization、Product/Service、Course、FAQPage 等类型，只标记页面真实可见内容。不机械要求每个客户增加 30 条 FAQ，不把标签缺失等同于 AI 不收录。

## 3. 仅通过 bb-browser 实测

复用全局安装及现有受管浏览器登录态。**本 skill 不使用 Playwright、不自行连接 CDP/调试端口，也不导出、复制、注入 cookies 或创建浏览器 profile。** bb-browser 内部传输由工具负责，不等于诊断脚本应自行管理 CDP。

先运行并读取结果：

```bash
bb-browser --version
bb-browser --help
bb-browser status --json
bb-browser tab list --json
```

若已连接但 open/tab list 返回 `No page target found`，用 `bb-browser tab new '<平台URL>' --json` 新建本轮标签再取 ID。未安装或未连接时，报告具体状态并请用户完成 bb-browser 设置/登录；继续网站审计与题库工作，不退回旧采集方案。参考 [bb-browser 官方仓库](https://github.com/epiral/bb-browser)，参数以本机 `--help` 为准（本次验证版本 0.14.2）。

### 每题操作

1. `bb-browser open '<平台URL>' --json`，读取返回的真实 tab ID；必要时解包 result，不能猜测 ID。
2. `bb-browser snap -i --tab '<tab-id>' --json`，确认新会话、登录态、输入框和发送按钮。**后续每个页面命令显式携带 --tab**；ref 使用快照实际值，页面变化后重新读取。
3. `bb-browser fill '<input-ref>' '<原题>' --tab '<tab-id>'`，再 click 发送按钮或 press Enter。每个平台先小样验证；超时先检查是否已发送，避免重复提问。
4. 短间隔读取 snap/get text，检查用户消息确为原题、回答不再流式生成。通常连续两次内容稳定且结束标记可见后采集，不把“等待 10 秒”当完成信号。默认单题最多 180 秒；超时留档，可记录一次恢复尝试，仍失败则记缺测。
5. 保存快照及 `bb-browser screenshot '<证据路径>.png' --tab '<tab-id>'`。通过快照或 `bb-browser eval '<只读取可见DOM的JS>' --tab '<tab-id>' --json` 提取**本题对应的最终回答**，排除输入框、历史消息、导航和思考区。选择器根据当前页面确认，不照搬历史 class 名。
6. 打开该回答来源面板，分别保存正文引用与检索/参考来源，记录 URL、标题、来源类型与完整性。只有标题则注明 URL 未取得，不拼接假 URL。必要时滚动补截图，检查截图文件确实生成。
7. 逐条落盘后继续；浏览器交互串行执行。只关闭本轮创建且已取证的 tab，保留用户其他页面及登录状态。

如果前台焦点问题无法用当前 bb-browser 完成，记录阻塞并请用户切到对应 tab；不调用原生 CDP 激活接口。登录、验证码、限流、拒答、超时、截断分别记录，不能标为“未提及”。不要为修复采集上传客户内部资料或调用未公开聊天接口。

原始记录至少含：问题 ID/原文、平台、会话 URL、时间、可见模型/模式、账号上下文限制、状态/失败原因、完整最终回答、来源及类型、快照/截图路径、bb-browser 版本。原始记录与人工标注分开保存。

## 4. 标注与 Profound 指标

计算前阅读 [references/profound-metrics.md](references/profound-metrics.md)，遵守分母、去重、缺测及数据结构定义。

- 标注目标与竞品出现情况、首次文字顺序、引用、叙事/情感、事实问题。提及不等于推荐，否定语境仍是提及。关键词匹配仅辅助，人工复核同名、歧义、品牌/产品层级和否定。
- 主指标包括条件可见率 Visibility、全部有效回答覆盖率、限定集合 Share of Voice、首次文字位置、Citations、Sentiment、FactCheck。分别列平台、topic 和题目证据，缺项显示 N/A + 原因。
- 私有位置/情感算法不能伪称复现，替代指标写明项目口径。无真实 Prompt Volumes、Agent Analytics、GA/CRM 数据，不生成需求量、抓取率、转化或 ROI；无可比历史批次不画趋势。
- 每个结论附证据 ID，区分定性推断与实测事实。注明“参考 Profound 公开指标的项目适配诊断，非 Profound 平台产出”。

## 5. 写客户版正文

读者是客户的老板、市场和技术负责人，不是做诊断的人。他们要在第一屏读懂三件事：**发生了什么、为什么值得处理、先做哪三件事**。方法、口径和工具是复核用的，只放在含证据附录版里，客户版不出现附录。以下规则都来自真实交付后的客户审阅意见。

**按“现象 → 原因 → 行动”组织，每条内容只出现一次。** 发现写现象（未被发现、事实答错），最后一条写原因（例如 AI 引用的是外部页面而非官网）；每条发现自带证明它的表格，并列出对应行动编号；行动表每行注明对应发现。不要另设“改善优先级”“证据对照”章节去重复同一批内容——审阅时读者最反感在三处看到同样的建议、又对不上编号。不属于主结论但影响信任的情况（企业背景评价、夸大的效果数字）放“另需关注”，同样挂行动编号。

**图文之间也不重复。** 图表或表格已经展示的数字与条目，正文说明里不再复述，只写图上看不出的解读（例如“AI 推荐的正是客户的路线，却点了别家的名”）；同一处问题只用一种形式呈现：原话卡片、对照表、截图三者择一（例如答错的参数用对照表，“没有官方参数表”这类说法用原话，准确度表就只列答对和缺依据的项）；含证据附录版的附录只放正文没有的内容（审计范围、未决事项、方法与限制、完整回答），不重写一遍发现，`sections` 按这个标准写；合作方案说明我们交付什么价值，不复述行动表的动作描述。首屏的发现标题与行动名称是目录式跳转，不算重复。

**原因类发现要用官网审计结论支撑。** 官网审计的范围与未决事项放含证据附录版，但“官网已有什么、缺什么”的结论必须进正文（用 `site` 检查图），因为它决定了行动是“修外部内容”还是“建官网内容”。来源统计要限定在与结论相关的回答范围内（例如只统计点名品牌的回答），不要用全部回答放大比例。

**首屏是“诊断快照”，只用计数，不用百分比。** 小样本下"0%""N/A"会被读成"品牌整体表现为零"。渲染器自动生成快照：被发现 / 被说对 / 被引用 / 官网基础（点名题里品牌必然被提到，不单列“提及”卡），每项是“x / n 条回答”这样的计数加“良好 / 一般 / 较弱”评级（参考 Profound 免费报告的 good/fair/poor 快照）。发现标题用事实句，例如"本轮 6 个未点名品牌的采购问题中均未获提及"，并保留范围限定（平台、题数、单日单账号）。百分比指标卡只在指标附录出现，始终带分子/分母。

**摘要用 2–3 句讲清现状、偏差和建议方向。** 示例：

> 某品牌已能被豆包识别品牌身份，但尚未在本轮 6 个未点名品牌的采购问题中获得提及。点名询问后，部分型号参数及质保信息与官网公开资料不一致，可能影响客户选型判断。建议优先统一产品资料与外部传播内容，再围绕三个重点场景提升被发现的机会。

**点名后的提及率不要当成认知准确率。** 题目里写了品牌名，回答里自然会出现品牌名。不要写"提示后 9/9 提及"，而写具体事实：哪些回答正确（主体、地址），哪些不准确（参数、质保）。

**每条关键发现写业务影响。** 例如参数偏差会影响客户选型，未获提及意味着采购初筛阶段缺席。

**行动建议必须承接诊断发现，先查已有资产。** 客户官网已有参数表、质保说明、FAQ、Schema 时，优先任务是核查外部内容与官网的一致性、改善型号资料被检索和引用的方式、再复测，而不是建议"新建参数表/FAQ"。每条建议能指回某条发现。

**敏感的未核实说法不在正文复述。** 企业人员规模、司法、资质等模型说法在正文里只概括为"出现需核验的企业背景评价，可能影响采购信任"。原句不进入客户版，只保留在含证据附录版的证据附录，并明确标注为"模型原句，非本报告认定"（撰写客户版时由撰写者给这类 claim 加 `sensitive: true`，不改动判定；渲染器会自动处理）。不要把它写成企业风险结论，也不要在核验表里反复出现原句。

**正文统一用中文业务语言。** natural/branded、complete/incorrect、raw_url、citation_status、工具名与版本、字段名、文件路径、链接清洗过程不出现在正文；需要时写进附录的方法说明。渲染器会把状态、题型、判定翻成中文。

**90 天计划用一张表，不用长段落。** 每行一个动作：编号（A1…）—优先级（P0/P1/P2）—动作—交付物—负责人—时间—验收方式—对应发现。P0 放产品事实纠正这类会直接误导客户的问题；首屏“建议先做”自动取排序后的前三项，所以排序要与摘要里的建议一致。

**图文并茂：每个图都要证明一条发现。** 用 `key_findings[].charts` 把自动图表放进它所证明的发现里，而不是集中成一个“数据看板”章节。可选图表（均由记录自动计算，不手填）：

| 键 | 图 | 典型放在 |
|---|---|---|
| `visibility` | 未点名问题中各品牌被提到的次数（目标高亮、竞品灰色，标 n/N） | “没被发现”类发现 |
| `matrix` | 逐题 × 品牌出现矩阵（首次出现顺序），客户能一眼看到自己在哪些问题里缺席 | 同上 |
| `facts` | 事实核验的一致 / 答错 / 缺依据堆叠条 | “被说错”类发现 |
| `sources` | 各类来源在未点名 / 点名回答中的出现次数；配 `source_categories[].play` 写每类来源的对应打法 | “原因”类发现 |
| `gaps` | 竞品被提到、目标缺席的回答里 AI 最常用的外部网站——直接变成后续外联与铺设清单 | 同上 |
| `site` | 官网 AI 就绪度检查（`site_checks`，已具备 / 可加强 / 缺失） | 同上 |

再配两类“眼见为实”的材料：`quotes`（AI 原话卡片，必须逐字出现在该题回答中，渲染器会校验）和 `screenshots`（回答截图，内嵌）。每条发现 1–2 句原话、0–2 张截图即可，挑最能让客户“看见问题”的那句——最有说服力的往往是“AI 推荐的正是客户的技术路线，却点了别家的名”这类句子，值得逐题找。

**不画在小样本下会误导的图。** 单批次不画趋势线；不给综合“AI 可见度 100 分”；不画情感雷达或象限图；不报小数点百分比和平均排名小数。这些是持续监测的价值所在，正好留给合作方案。

**以“合作方式”收尾，但只卖报告里证明过的事。** `engagement` 写 2–4 项后续服务，每项注明对应的行动编号、交付物和周期；开头如实说明“这是单平台单日快照，改动是否见效需同口径复测证明”。不写没有依据的 ROI、流量或排名承诺。`provider` 填我们的机构名与网址，渲染为页眉署名和“预约结果解读”按钮。

**定稿范例。** [references/example-report.json](references/example-report.json) 是用户确认的最终格式的客户版正文字段（取自一次真实交付，品牌、型号、网址与竞品已脱敏为虚构名称）：摘要、三条发现（现象 → 现象 → 原因，各自带图表、原话或截图）、两条另需关注、8 个行动、三项合作方案。写新报告前先读它，照它的结构、篇幅和语气写；数字、结论和原话全部换成新客户的实测结果，不照搬。

## 6. 生成最终 HTML

使用 [assets/report.html](assets/report.html) 和 [scripts/render_report.py](scripts/render_report.py)，输入结构见 [references/profound-metrics.md](references/profound-metrics.md)。把正文内容写进报告 JSON 的结构化字段，**不要再写一次性的构建脚本去替换 HTML 片段**——图表用 `charts` 自动生成，人工对照表放进对应发现的 `tables`，截图放 `screenshots`。所有计数从记录里算，不手填。

```bash
python3 '<skill目录>/scripts/render_report.py' '<诊断目录>/<品牌名>_AIEO诊断报告_<日期>.json'
```

脚本仅用 Python 标准库校验数据、计算指标，在 JSON 同目录输出客户版 `.html`、`_含证据附录.html` 和 `.metrics.json`。客户版不带附录——客户审阅时反馈附录内容多、与正文重复，读者只需要正文；复核材料由含附录版和证据包承担，正文里的引用会自动写成“见证据包”。原文按文本转义，不直接插入可执行 HTML。报告固定顺序：

1. **封面与诊断快照**（`summary` + `scope_note` + 自动快照卡 + 每条发现的标题与业务影响 + 前三项行动）。
2. **发现与证据**（`key_findings`，3–5 条，按现象 → 原因排列）：每条含业务影响、说明、`charts`、`quotes`、`tables`、`screenshots`、证据题号和 `actions` 行动编号。
3. **另需关注**（`notes`，可选）：不是主结论但影响信任的情况，同样挂行动编号。
4. **行动计划**：自动 90 天路线图（甘特条，颜色深浅 = 优先级，`timing` 写成“0–30 天”格式）+ 行动表（带编号并反向标注对应发现）。每个行动必须被至少一条发现或关注引用，否则渲染会报错。
5. **合作方式**（`engagement`，可选但对外报告应填）。
6. **附录（仅含证据附录版）**：品牌背景与官网审计范围（`sections`）→ 采样方法与限制 → 指标附录（Profound 参考指标）→ 完整回答证据。`sections`、`methodology`、`limitations` 仍需认真写，它们是复核版的内容。

图表是纯 HTML/CSS（手机宽度下文字不缩小），每个图附“查看数据表”并在标记上提供悬停提示；颜色只承担身份或状态，状态始终配图标与文字。保留导航、响应式表格、键盘操作及打印样式；不引入前端框架或 CDN。禁用 JavaScript 时正文及指标仍可阅读。生成后在桌面与手机宽度（约 390px）各看一遍：没有横向滚动、标签不重叠。

最后运行 `python3 '<skill目录>/scripts/package_evidence.py' '<报告.json>'`，把含证据附录版 HTML、报告 JSON/metrics、问题库、`evidence/` 和同目录的说明文件打成证据压缩包，与客户版 HTML 一起交付。脚本用 Python `zipfile` 写 UTF-8 文件名（macOS 自带 `zip` 打出的中文文件名在 Windows 上会乱码），并确认压缩包里没有客户版 HTML。同目录里其他要随包提供的文件（采样计划、人工复核记录、技术说明等）用 `--extra 文件名` 逐个加入，不该外发的文件（例如旧版报告截图）用 `--exclude '通配符'` 排除。

## 7. 交付检查

按 [CHECKLIST.md](CHECKLIST.md) 检查。运行 `python3 '<skill目录>/scripts/render_report.py' --check` 与 `python3 '<skill目录>/scripts/package_evidence.py' --check`；真实数据另行构建，复核至少一条命中、一条未命中、一条缺测与一个来源记录。

通过 bb-browser 打开 HTML（不支持本地文件时用仅绑定 127.0.0.1 的临时静态服务），检查导航、筛选、窄屏和打印。检查后关闭本轮预览 tab/服务。工具无法把窗口调到约 390px 时，如实写明“未做手机宽度检查”，不假称通过。无法打开时披露未完成视觉验收，不假称通过。

交付 HTML、证据压缩包、问题库和可复核数据路径。部分缺测可交付，但摘要必须说明覆盖范围，不把未完成的实测写成全平台完成。
